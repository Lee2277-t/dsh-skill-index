# dsh-skill-index

把本机技能库接成 DSH 工具：检索、按需读、记台账。

**解决的问题**：技能多了以后只有两条路——要么把所有描述塞进系统提示（173 个技能的 description 合计约 2.6 万 tokens，每轮都付），要么全靠模型自己想起来去翻文件（经常想不起来）。这个插件给第三条：**按需检索 + 两级加载 + 每轮自动提示**。

## 工具

五个工具，schema 合计约 420 tokens/轮。

### `skill_search`

按关键词检索。每条一行的紧凑格式，带上下文成本和族规模：

```
Matched 2 of 173 indexed skills for "小程序 隐私":

- wechat-miniprogram-privacy-audit [02-微信小程序] 54 ·全文≈0.6k ·族:wechat(4) — 扫描微信小程序可能涉及隐私的接口…
- wechat-miniprogram-asset-audit [02-微信小程序] 42 ·全文≈1.6k ·族:wechat(4) — 在小程序资源体积检查失败或明确要求清理资源时…
```

- `全文≈0.6k` 是**读全文要花的 token**（字符数 / 1.6），和 `skill_read` 报的是同一个数。
- `·族:seo(25)` 表示这个技能是 25 个 SEO 子技能之一，不是独立工具。
- 不给路径：读要走 `skill_read`，那才会记账。
- 命中不足时只报名字，不铺描述。

### `skill_read`

默认给 digest（约 300 tokens）：

```
# wechat-miniprogram-privacy-audit  [02-微信小程序]
全文 ≈0.6k tokens · <skills-root>\小程序隐私合规审计\SKILL.md

不适合：静态扫描不等于平台规则核验或合规结论，也读不到后台配置状态

扫描微信小程序可能涉及隐私的接口、组件、声明与失败处理…

```

`mode: "full"` 才载入整份 SKILL.md。名字有歧义时拒绝猜，直接列出候选。

### `skill_active`

看本会话加载了哪些技能、各占多少 token、多久之前读的，最后一行是自动提示的状态。

### `skill_drop`

任务变了就停用不再适用的技能。**它改变行为，不改变上下文体积**——正文已在历史里，真释放要等压缩。

### `skill_catalog`

按分类列全部技能。category 过滤用的是目录名（中文），例如 `02-微信小程序`、`10-网站与部署`。

## 检索是怎么打分的

元数据命中按名字 > 目录 > 分类 > 描述 > 标题的顺序加权，描述层面的命中再按**稀有度**打折——
「清理」出现在好几条描述里，「对账」只在一个名字里，后者信息量更大。

中文查询不靠空格：`去水印` 会拆出 `去水`、`水印` 两个二元组，所以能命中「去**AI图片**水印」。

库里有相当一部分技能只有英文描述（`better-*`、`seo-*`）。一张手工维护的双语词表负责搭桥，
权重打折——**翻译来的词只算半个证据**，中文精确匹配优先。

**正文兜底**：元数据一个都没命中时，才去正文里找。即使找到也只当**线索**报出来，不冒充命中：

```
没有元数据强匹配。正文里出现过这些词：webfont-subsetting(7)
只是线索，不算命中——用 skill_read 看一眼 digest 再决定，别直接照做。
```

判据是「是否出现在正文开头」或「是否反复出现」——一个词在万把字的正文里出现一次，不构成证据。

## 自动提示

每个 turn 的第一步，用用户自己的话检索一次；分数 ≥ 14 就在运行时上下文里加一行（约 50 tokens）：

```
[技能库] 可能有用的技能：wechat-miniprogram-privacy-audit（全文≈0.6k）。要按它做就 skill_read；不适用就忽略，不必回应这句。
```

抑制规则（全部会实际生效）：

- 只在 `step === 1`
- 整句就是接续词（"继续"、"好的"、"ok"）不提示；**"再查一下字体"不会**被当成接续
- 少于 2 个字符不提示
- 分数低于 `autoHintMinScore`（默认 14）不提示
- 同一会话同一个技能只提示一次

**已知限制**：`systemPrompt.context` 拿不到 agent 身份，所以提示是进程级的，不是会话级的。
同时跑多个 agent 时，理论上先装配的那个会取走提示。单会话使用不受影响。

## 评测

`eval/` 下有一套可复现的评测，42 条查询（40 正例 + 2 负例）。

```bash
node eval/run.mjs            # hit@1 / hit@3 / MRR / 每次检索的 token
node eval/audit-fields.mjs   # 复核 when-not-to-use 字段
```

当前（173 个技能）：

| 指标 | 值 |
|---|---|
| hit@1 | 90.5% |
| hit@3 | 97.6% |
| MRR | 0.942 |
| 单次检索输出 | ≈257 tokens |

评测**只覆盖元数据路径**，正文兜底、自动提示、软链库这类路径不在里面——它们由独立的破坏性测试覆盖。

## 省了多少

固定开销（每轮都在上下文里）：5 个工具 schema 约 420 tokens，`AGENTS.md` 那段约 275。

| 动作 | 成本 |
|---|---|
| 检索一次 | ≈257 tokens |
| 读 digest | ≈300 tokens |
| 读全文 | ≈4,500 tokens（12 个样本均值） |

省的是「判断」不是「执行」：读一个技能就照着做，要比直接读全文多付约 300；
省下来的是**看了但没用的候选**，每否掉一个省约 4,150。

所以它划算的前提是**探询比**——一场活里"看了没用"超过三次，才回本。

## 配置

| 键 | 默认 | 说明 |
|---|---|---|
| `roots` | `["~/.skills"]` | 技能库根目录，可多个 |
| `maxResults` | 8 | 检索默认返回条数 |
| `refreshSeconds` | 300 | 索引缓存时长 |
| `autoHint` | true | 关掉自动提示 |
| `autoHintMinScore` | 14 | 自动提示的分数门槛 |

## 索引行为

- 跟随目录软链（用 junction 组织的技能库能正确索引），并做环检测。
- 去重键是 `name + folder`：只按名字去重会让同名但不同目录的技能静默消失。
- frontmatter 不按行数截断——头部很长的技能不会退化成"没有描述"。
- 索引缓存按 roots 分键：同一进程挂多份时不会拿错库。
- 正文只留前 8KB 做兜底检索。

## 使用账本

`<home>/.skill-hub/usage.json` 记读取次数，用于让读过的技能排前面（最多 +120%，十次封顶）。

按 mtime 判失效：删掉文件或别的进程改过都能立刻生效。删掉文件就回到原始排序。

## when-not-to-use

可选的 frontmatter 字段，digest 里排在描述**前面**：

```yaml
when-not-to-use: 不是字体设计或选型；不判断授权；缺字检查需 ttf/otf 原件（woff/woff2 读不了 cmap）
```

一句、具体、不写套话。`eval/audit-fields.mjs` 会挑出太长、套话、泛开头、重述描述的四类。

## 限制

- **语义检索缺失**：只有关键词、二元组、词表和正文兜底，同义词靠手工词表，不是向量检索。
- **正文兜底是线索，不是命中**，分数天然低，只报名字。
- **自动提示是进程级**，多 agent 并发时可能串。
- **评测集只有 42 条**，能防回归，不能证明线上一定准。
- **技能重叠没消除**：家族标注只是让人知道"这是套件里的兄弟"，不代表选对了。
